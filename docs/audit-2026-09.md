## Summary

Four critical findings and eighteen high ones. They cluster into three groups, and the groups are independent of each other.

**The billing system is open.** Anyone holding the publishable key, which ships in the client bundle of a public repository, can grant themselves unlimited AI credits. Three separate mechanisms allow it: the credit-granting database functions are executable by the anonymous role, the three billing tables carry policies that apply to every role, and the coach honours a bypass flag sent in the request body. Each one is sufficient on its own, so all three must be closed. I confirmed the first two against the live database rather than inferring them from the migration files.

**Finished workouts can be lost.** The save path fires its write without awaiting it, then deletes the only local copy and leaves the screen. On a gym phone with no signal the workout is gone with nothing to retry from. The codebase already solved this problem for templates, with a documented queue; sessions never got one.

**Read-back surfaces disagree with what was logged.** Editing a saved workout erases its distances. Band levels are run through a unit conversion. Custom timed exercises render as weight and reps once you leave the logging screen. A 30-minute run reads as "1800 min". Each is small; together they mean the history a user reviews is not the history they recorded.

Two operational facts sit behind several findings. The function deploy workflow has failed on all twenty runs since May because a secret is empty, which is why the program generator still runs the May build and is missing its authentication guard. And the AI credit price is set to the Opus 4.1 rate, so every user is billed three times what the calls actually cost.

## Recommended order of work

Ordered by exposure, not by effort. The first three are small changes that close unbounded spend; the fourth is the only one that risks user data today.

1. **Close the three billing bypasses.** One migration revoking execute and dropping the three policies, plus deleting the god-mode flag from the edge function. Each path alone gives an anonymous caller unlimited spend on your Anthropic key, so partial fixes buy nothing. Unblocks charging real money for anything.
2. **Fix the deploy workflow secret, then redeploy both functions.** Every server-side fix below is inert until this works. It also ships the program generator's missing authentication guard, which has been written and unshipped since July.
3. **Correct the token price to the Opus 4.7 rate.** A four-line constant change. Until it lands, every allowance, ledger row and cost figure is wrong by 3x, so you cannot reason about margin or size a paid tier.
4. **Make the workout save await its result before clearing the cache.** The only finding here that destroys user data in normal use. Mirror the template queue that already exists, and the offline case stops losing workouts.
5. **Fix the four read-back surfaces: distance on edit, band conversion, custom input modes, and the seconds-as-minutes labels.** Cheap, independent, and each one currently makes the app look broken to the user who notices it. Doing them together needs one pass over the summary and history components.

## Critical (4)

Data loss, a security hole, a money leak, or the app unusable.

### 1. A failed save loses the entire workout, with no queue and no way back to the summary screen

**Severity:** Critical · **Category:** data-integrity
**Where:** `src/hooks/useStorage.ts:477`

**What is wrong.** `saveSession` awaits its upsert and, on error, toasts and returns **before** `setHistory` runs, so the finished workout never enters app state and never reaches the localStorage snapshot. The caller makes that unrecoverable: `Index.tsx:337` fires `saveSession` without awaiting it, then in the same tick calls `clearSessionCache()`, nulls the summary and switches to the dashboard.

The Supabase client does not throw on a dead network: postgrest resolves `{ data: null, error, status: 0 }`. So an offline Save takes the error branch quietly. Templates have a durable queue for exactly this case (`pendingTemplateWrites`); sessions have none.

**Failure scenario.** User finishes a workout at the gym with no signal and taps Save on the summary. Index calls saveSession without awaiting it, then synchronously clears the active-session localStorage cache and navigates to the dashboard. The upsert resolves with a status-0 error; saveSession toasts and returns. The session is now in no state (setHistory never ran), not in localStorage (cache cleared), not in the DB, and the summary screen is gone. The whole workout is lost. CLAUDE.md's pending-template design assumes this cannot happen ('the session itself still saved, because the user was sitting on the summary screen and could press Save again') — but onSave leaves the summary screen before the write resolves.

**Fix.** Give saveSession the same durability as saveTemplate: on error apply the session locally, park it in a pending-sessions queue (same pattern as pendingTemplateWrites), and replay it on the next successful load; return a boolean so Index can keep the summary screen up (and not clear the session cache) when the save fails.

**How it was verified.** Not executed (needs a mocked Supabase failure inside a hook). Traced statically: postgrest-js index.mjs:293-330 confirms fetch rejection -> error payload; useStorage.ts:477-481 returns without setHistory; Index.tsx:339-342 clears the cache and navigates synchronously.

Two independent reviewers examined it, one instructed to reproduce it and one instructed to refute it; both concluded it is real.

### 2. Any signed-in user can switch off AI billing with a request-body flag, and the unlock phrase ships in the public bundle

**Severity:** Critical · **Category:** security
**Where:** `supabase/functions/ai-coach/index.ts:544`

**What is wrong.** The edge function reads `god_mode` straight out of the request body and sets `bypassMetering = god_mode === true || phraseInMsg`. That skips the pre-call balance gate and, after the call, writes a `delta_micros: 0` ledger row instead of debiting. Nothing ties the bypass to a user id, a role, or an environment.

The unlock phrase is an exported constant in `ChatContext.tsx:386`, so it is a string literal in the deployed JavaScript, and the repository is public. Sign-up is open.

**Failure scenario.** Any authenticated user (Google sign-in is open) either types 'god mode 3247' in the coach chat or POSTs to /functions/v1/ai-coach with their own JWT and `{"messages":[...],"god_mode":true}`. The only server-side check is that userId exists; there is no admin/allowlist check. The pre-call balance gate is skipped and the post-call ledger writes delta_micros: 0, so the user (including one already at 402) gets unlimited claude-opus-4-7 turns (MAX_TOKENS 8000, ~26k-token context) billed to the operator's ANTHROPIC_API_KEY with no cap and no visible spend in their balance.

**Fix.** Remove `god_mode` from the request contract and the phrase check from the edge function. If an operator bypass is needed, decide it server-side on something the client cannot set (e.g. a `profiles.is_admin` column no user RLS policy can write, or an allowlist of user ids in a function secret `METERING_BYPASS_USER_IDS`), computed after `supabase.auth.getUser(token)`. Stop exporting GOD_MODE_PHRASE from ChatContext/AIChatBubble, rotate the phrase, and redeploy ai-coach (the bypass is live at v4).

**How it was verified.** Traced statically; no runtime API call possible. Verified via grep that no test, migration or RLS policy constrains the bypass and that both client fetch sites forward `god_mode`.

Two independent reviewers examined it, one instructed to reproduce it and one instructed to refute it; both concluded it is real.

### 3. Every user, and anyone holding the public key, can rewrite their own AI credit balance

**Severity:** Critical · **Category:** security · **Confirmed on the live project**
**Where:** `supabase/migrations/20260518000000_token_credits_and_iap.sql:27`

**What is wrong.** A Postgres policy with no `TO` clause applies to **every** role, and permissive policies OR together, so the owner-only `SELECT` policies beside these are irrelevant. On the live database all three show `roles={public}`, `cmd=ALL`, `qual=true`.

The same mistake was found and fixed in April for `user_ai_usage` and `ai_error_log` (migration `20260411023736` drops and recreates them `FOR ALL TO service_role`). The May token-credits migration reintroduced it on three new tables.

**Failure scenario.** A policy with no TO clause applies to every role; permissive policies OR together so the 'Users can view own balance' SELECT policy is irrelevant. Any signed-in user runs from the browser console `supabase.from('user_token_balance').update({ free_used_micros: 0, paid_balance_micros: 1e12 }).eq('user_id', myId)` and the ai-coach/generate-program gate (balance.ts getOrInitBalance -> gate) passes forever at the operator's Anthropic expense; they can also delete their own token_ledger rows to erase the audit trail. Because the policy also applies to anon, anyone holding only the public anon key (shipped in the JS bundle) can, with no login, read/update/delete every row in all three tables for every user — wiping balances, forging iap_purchases with status 'granted', or deleting a purchase row so the transaction_id idempotency guard no longer blocks a replay.

**Fix.** New migration: DROP POLICY "Service role full access balance" ON public.user_token_balance; DROP POLICY "Service role full access ledger" ON public.token_ledger; DROP POLICY "Service role full access purchases" ON public.iap_purchases; (service_role bypasses RLS, so no replacement is needed; if wanted for symmetry recreate with `FOR ALL TO service_role`). Additionally REVOKE INSERT, UPDATE, DELETE, TRUNCATE ON those three tables FROM anon, authenticated. Apply with `supabase db push` and verify with pg_policies / get_advisors.

**How it was verified.** Two independent reviewers examined it, one instructed to reproduce it and one instructed to refute it; both concluded it is real.

Correction from the refuting reviewer: Two details in the failure scenario overstate slightly: (1) forging an iap_purchases row with status 'granted' does not by itself credit any balance — balance is only changed by grant_tokens/consume_tokens or a direct write to user_token_balance; the purchase row is only a record (grant-tokens/index.ts:72-90 inserts it separately from grantPaid). (2) The transaction_id replay concern is theoretical today: the only writer generates `stub:${crypto.randomUUID()}` (grant-tokens/index.ts:69), so the UNIQUE guard never fires in Phase 1. The core claim — anon and authenticated get unrestricted SELECT/INSERT/UPDATE/DELETE on every user's balance and ledger, so anyone with the public anon key can mint themselves unlimited AI credit and erase the audit trail — is correct as written.

### 4. The credit-granting database functions are callable by anonymous clients

**Severity:** Critical · **Category:** security · **Confirmed on the live project**
**Where:** `supabase/migrations/20260518000000_token_credits_and_iap.sql:236`

**What is wrong.** Both functions are `SECURITY DEFINER`. The migration tries to lock them with `REVOKE ALL ... FROM PUBLIC`, but Supabase grants `EXECUTE` on new functions in `public` explicitly to `anon`, `authenticated` and `service_role` through default privileges, not through `PUBLIC`. The revoke therefore removes nothing.

I confirmed this against the live catalog: `has_function_privilege` returns true for `anon` on both functions. Because `SECURITY DEFINER` runs as the owner and ignores row-level security, fixing the policies above does **not** close this.

**Failure scenario.** Any signed-in user (or anyone with the public anon key) calls `supabase.rpc('grant_tokens', { p_user_id: '<any uuid>', p_micros: 1000000000000, p_reason: 'admin_grant', p_reference: 'x' })`. The function runs as its owner, credits the balance, writes a legitimate-looking 'admin_grant' ledger row and returns success; the ai-coach gate passes forever and the operator pays Anthropic. The x-admin-secret protection on grant-tokens/index.ts:21-28 is bypassed entirely because the RPC underneath it is reachable directly. Conversely `consume_tokens` with a huge p_cost_micros drives any victim's paid balance deeply negative (`-- may go slightly negative`), locking that user out of the coach.

**Fix.** REVOKE EXECUTE ON FUNCTION public.consume_tokens(uuid, bigint, text, text) FROM anon, authenticated; REVOKE EXECUTE ON FUNCTION public.grant_tokens(uuid, bigint, text, text) FROM anon, authenticated; (keep the service_role grant). Consider `ALTER DEFAULT PRIVILEGES IN SCHEMA public REVOKE EXECUTE ON FUNCTIONS FROM anon, authenticated` so future RPCs are opt-in, and add a runbook check running has_function_privilege for every SECURITY DEFINER function.

**How it was verified.** Two independent reviewers examined it, one instructed to reproduce it and one instructed to refute it; both concluded it is real.

Correction from the refuting reviewer: Nothing material to correct. Minor precision: the abusive consume_tokens/grant_tokens call must pass a p_reason within the token_ledger CHECK list ('ai_coach','generate_program','iap_purchase','iap_subscription','admin_grant','refund_adjustment', migration lines 41-44) or the ledger INSERT aborts and rolls the whole function back — 'admin_grant' as used in the finding is valid, so the scenario stands. Also note this hole is independent of c4-token-tables-open-rls: fixing the RLS policies does not close it, because SECURITY DEFINER runs as the owner and ignores RLS.

### 5. Editing a saved workout erases every distance in it

**Severity:** High · **Category:** data-integrity
**Where:** `src/components/ActiveSession.tsx:173`

**What is wrong.** `editBlocks` rebuilds each stored set into an editable row carrying weight, reps, RPE and time, but never `distance`, even though both the row type and the stored set have the field. The input renders blank, and `finishWorkout` then writes `distance: undefined` over the original row.

### 6. Band levels are run through the pounds-to-kilograms conversion, corrupting them on save

**Severity:** High · **Category:** bug
**Where:** `src/components/ActiveSession.tsx:1027`

**What is wrong.** `usesWeight` excludes only the two distance modes, so it returns true for `band`. On finish, the band's level (1 to 6, chosen from a dropdown) is passed through `toKg`, which for a lbs user multiplies by 0.4536.

The sibling path proves the omission: the update-template branch 100 lines earlier calls `inputToTargetWeight(..., mode === 'band')` with an explicit flag to skip conversion. kg users are unaffected because `toKg` is the identity there, which is why the existing tests miss it.

**Failure scenario.** A user whose weight unit is lbs logs a band exercise at level 3 ('Medium') and finishes. The saved WorkoutSet.weight is 1.360777. The summary shows 'Level 1.36', history shows 'Level 1.36 × 10', StrengthTab shows 'Lv 1.36', and next session's Previous column shows 'Level 1.36'; tapping it writes '1.360777' into the select, which matches no option so it renders blank. kg users are unaffected (toKg is identity), which is why kg-centric tests miss it.

**Fix.** Skip the unit conversion for band mode when building WorkoutSet rows in finishWorkout (parent sets and drops): `weight: mode === 'band' ? parseFloat(s.weight) || undefined : usesWeight(mode) ? ... toKg(...)`. Apply the symmetric guard in editBlocks (line 166/175 `fromKg(s.weight, weightUnit)`).

**How it was verified.** Throwaway vitest: ActiveSession with cachedSession containing band-chest-press, set {weight:'3', reps:'10', completed:true}, weightUnit 'lbs', startTimestamp 60 s ago; click 'Finish' → onFinish set weight ≈ 1.360777 (toBeCloseTo 5 decimals). Same with weightUnit 'kg' → weight 3. Both passed. File deleted.

Two independent reviewers examined it, one instructed to reproduce it and one instructed to refute it; both concluded it is real.

Correction from the refuting reviewer: Minor: with the repo's KG_TO_LBS = 2.20462 and 6-decimal storage rounding, level 3 stores as 1.360779, not 1.360777. Note also that the edit path is not itself broken for an lbs user: fromKg(1.360779,'lbs') rounds back to 3 (one decimal), so the select re-matches on edit; the symmetric editBlocks guard is only needed once finish stops converting.

### 8. The credit-granting admin secret is shipped to the browser whenever the feature is enabled

**Severity:** High · **Category:** security
**Where:** `src/components/CreditsScreen.tsx:71`

**What is wrong.** Vite inlines every `VITE_*` variable into the shipped JavaScript at build time. The in-app credit buttons are hidden unless `VITE_GRANT_TOKENS_SECRET` is set, so the only build in which the feature works is a build that publishes the secret.

The function behind it accepts an arbitrary `target_user_id` and an uncapped `micros`, checking only the static header. Its own file comment says the stub "must be disabled / hard-gated to an admin before public release"; nothing in the repository enforces that.

**Failure scenario.** Vite inlines every VITE_* variable into the JS bundle at build time. The only way the in-app 'Get more credits' buttons work is to set VITE_GRANT_TOKENS_SECRET in the Vercel build env, at which point the secret is a string literal in a public file that every user downloads. With it, any signed-in user calls grant-tokens with `{micros: 1e15}` (no cap) or `{target_user_id: <anyone>, pack: 'topup_large'}`; each call inserts a fresh random stub transaction_id so the UNIQUE index offers no replay protection, and grant_tokens has no ceiling. Nothing in the repo (no build check, test, or server kill switch) enforces the 'disable before public release' note, so the trigger is the first non-owner signing up while the stub is deployed.

**Fix.** Never read the secret in the client. Gate grant-tokens on the caller's identity: verify the JWT, then check `profiles.is_admin` (service-role-only column) or an allowlist of user ids in a function secret; drop x-admin-secret and its CORS header; drop `target_user_id` unless the caller is admin. Add an upper bound on `micros` and a per-day grant cap. Until Phase 2 IAP exists, keep the stub callable only from an operator tool with the service role.

**How it was verified.** Static trace only.

Two independent reviewers examined it, one instructed to reproduce it and one instructed to refute it; both concluded it is real.

Correction from the refuting reviewer: Exposure is conditional on the secret being set in the production build env, which the repo cannot confirm; the architectural defect (feature only works when the secret is public) is unconditional. Duplicate of c0-grant-tokens-secret-in-bundle.

### 11. A template set to "failure" can never be given a rep count again

**Severity:** High · **Category:** bug
**Where:** `src/components/TemplateBuilder.tsx:101`

**What is wrong.** The builder converts a template into blocks with `repsToFailure: ex.targetReps === 'failure'`, and converts back with `block.repsToFailure ? 'failure' : parseInt(...)`. Correction: Also affects time-based exercises: a timed set completes with reps blank, so after an accepted update-template prompt the builder's Time (min) cell is blank and typed minutes are discarded on save too.

### 12. Correcting one set silently rewrites the sets you already logged

**Severity:** High · **Category:** data-integrity
**Where:** `src/hooks/useBlockMutations.ts:65`

### 15. A backup restore reports success while silently discarding every rejected row

**Failure scenario.** The next `supabase db push`, whether from the runbook or the fresh-project setup, finds eight remote versions with no local counterpart and refuses. The repair it suggests then makes push replay already-applied files, and `CREATE TABLE public.user_token_balance` fails because the table exists. Anyone following the documented runbook lands in a half-applied state.

**Fix.** Run `supabase migration repair` to align the eight versions, or rename the files to the live versions. Then pick one apply path in CLAUDE.md, and if the MCP server stays, document that its version stamp must be copied back into the filename.

**How it was verified.** Compared the live schema_migrations table against the repository filenames. Eight of twenty-six differ, and two are out of order relative to each other.

## Method

Nineteen reviewers read the codebase in parallel, thirteen assigned to a subsystem and six to a cross-cutting lens such as security, concurrency or cost. A second round ran against the first round's findings so reviewers could look for what the others missed. That produced 300 raw findings, merged down to 222 distinct ones.

Every one of the 222 was then verified by reviewers who had not found it. Each read the cited file in full, traced the failure scenario, and looked for a guard, a test or a documented intent that would make the claim wrong. Where it was practical they wrote a throwaway test against the real module, ran it, recorded the result and deleted the file. Findings that carried a critical or high claim got a second reviewer whose only instruction was to prove the finding wrong.

195 survived, 10 were refuted outright, and 17 were disputed between the two reviewers. I adjudicated the disputes and the fifteen severity disagreements by reading both write-ups against the code. Where the two agreed a finding was real but disagreed on severity, I took the sceptic's level, which is the defensible floor. The exceptions are noted in each entry.

The database and deployment findings were confirmed against the live Supabase project rather than inferred from the repository: role privileges from the system catalogue, policies from `pg_policies`, the deployed function source diffed against the repository, and the deploy workflow's run history from GitHub. Those entries are marked.

What this did not cover: no code was executed against the live database, no load or penetration testing was done, the Anthropic API was never called, and the app was not driven in a browser. Findings about API behaviour rest on the vendor's own reference, which is cited where it matters.

| Stage | Agents | What it did |
| --- | ---: | --- |
| Find | 25 | Two rounds of subsystem and lens reviewers, second round told what the first had already reported |
| Merge | 5 | Clustered 300 raw findings into 222 distinct ones, sorted by file so near-duplicates met |
| Verify | 114 | Every finding re-examined by reviewers who did not find it; critical and high got a second, adversarial pass |
| Adjudicate | 1 | Disputes, severity disagreements and cross-chunk duplicates settled by hand against the code |

Every finding cites a file and line as of commit efffcd8. Reproduction notes name the test that was run. Nothing in this audit changed application code.
